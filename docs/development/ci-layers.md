# CI 分层：什么检查在哪里跑

三层，按"多久必须有一次"划分。每一层回答同一个问题：**这次的改动会不会破坏这一层负责的东西。**

| 检查 | PR | 夜间 | 发版前 | 负责什么 |
| --- | --- | --- | --- | --- |
| `architecture` 静态边界 | ✅ | ✅ | ✅ | 模块归属、导入方向、门禁基线 |
| `typecheck` 全量类型检查 | ✅ ubuntu | ✅ 三平台 | ✅ | 类型契约 |
| `test` 单元套件 | ✅ 定向范围 | ✅ 全量 + 覆盖率 | ✅ | 行为契约 |
| `build` 打包产物 | ✅ ubuntu | ✅ 三平台 + macOS 签名 | ✅ | 产物完整性 |
| Electron E2E | ❌ | ✅ | ✅ | 真实进程链路 |
| 跨平台矩阵 | ❌ | ✅ | ✅ | 平台差异 |

## PR 路径

`changes` job 解析改动范围，产出 `unit_scope` / `e2e_scope` / `build_scope`：

- `changed`——只跑受影响文件。源码与测试同属一次改动时，范围最窄。
- `full`——基础设施变了（`vitest.config.ts`、锁文件、`tsconfig`、包清单的依赖/脚本字段）时无法收窄，跑全量。
- `skip`——纯文档改动，不跑。

范围按**整个 PR 的 diff** 算，不按单个 commit：PR 里动过 `package.json` 这类基础设施，之后再推只改文档的 commit，范围仍然是 `full`（本 PR 就实测过一次纯文档提交仍解析出 `unit=full`）。

范围解析规则在 `scripts/ci/test-scope.mjs`，判定逻辑的测试在同目录的 `test-scope.test.ts`。

## 夜间路径

`schedule`（每日 20:20 UTC）跑三平台全量单元套件、覆盖率上传、跨平台打包与 macOS 产物校验，以及 Electron E2E。PR 路径不跑这些——它们要么太慢，要么当前产不出可用的信号。

## 手动路径

`workflow_dispatch` 跑与夜间相同的范围，包括 E2E。这是"我现在就要全套证据"的入口。

## 已知边界

- **E2E 不在 PR 路径上。** 套件当前无法区分"这次改动弄坏了"和"它本来就是红的"，红 job 不是门禁而是噪声。恢复条件写在 `.github/workflows/test.yml` 的对应 step 注释里。
- **单元套件的固定成本按文件计。** 1,178 个文件各自支付一次模块收集与环境初始化，这部分与用例数量无关。压这条成本要压的是"每个文件收集要多久"，不是"少写几个用例"。
