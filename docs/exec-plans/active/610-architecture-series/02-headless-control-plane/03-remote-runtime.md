### 0.2 已核实:小程序不支持 SSE

> 这一条**推翻了 Phase B §8 的推迟决定**,不是推翻它的原则。

实测外部资料(2026-10-05 查):

- 微信小程序**没有原生 `EventSource` API**;`wx.request` **不暴露流式读取**,
  响应体在 `onComplete` 时一次性交付
  ([稀土掘客](https://juejin.cn/post/7656681358269710379)、
  [CSDN 问答](https://ask.csdn.net/questions/8229869))
- `wx.connectSocket` **原生支持**,是官方推荐的实时通信方案
- `enableChunked` + `onChunkReceived` 可模拟,但被普遍标注为
  **不推荐**、需手工处理分片边界与 UTF-8 截断
  ([CSDN](https://blog.csdn.net/m0_53956340/article/details/150845428))
- 存在第三方 polyfill(`miniprogram-fetch-stream`),说明这是**长期痛点**
  而非配置问题

**结论:`apps/web` 用 SSE 没问题(浏览器原生支持),但小程序必须走 WebSocket。**

### 0.3 这恰好触发 Phase B 自己写的抽象条件

[02 §8](02-client-unification.md#8-传输先不抽象) 写的是:

> **判据:当第三个客户端出现、且它需要双向流时再抽象。**

小程序**就是**那个客户端,而平台限制证明它**必须**要 WebSocket。
**触发条件成立。**

所以:

- **B 阶段仍然不要抽象** —— 当时没有真实消费者
- **C 阶段必须抽象** —— 现在有了,而且是平台强制的
- **触发它的是小程序,不是"架构洁癖"**

> 抽象的理由必须写下来:**"因为微信小程序没有 EventSource。"**
> 写别的理由就是在给一个没有消费者的抽象找借口。

### 0.4 不必抄 ZCode 的二进制协议

ZCode 用 VS Code 风格二进制 RPC + `VSBuffer`
(`packages/client/src/websocket.ts:46-67`)。**duya 不需要** ——
小程序侧 `wx.connectSocket` 用 JSON 字符串收发最省事
(`socket.send({ data: JSON.stringify(...) })`)。
**抄它的"传输无关"结构,不抄它的"二进制载荷"。**

## 2. runtime 注册模型

### 2.1 方向:runtime 拨号出去,不是控制平面拨号进来

**runtime 主动连接控制平面并保持长连接。**

理由:远端电脑通常在 NAT / 防火墙 / 动态 IP 后面,要求它可被入站连接
不现实。反过来(控制平面拨号进 runtime)只在同局域网或 VPN 下成立。

> ZCode 的远程路径也是这个方向:`packages/server/src/remote/*` 走
> SSH 上传 + stdio(`remote/backend.ts:43-46`),浏览器经 `/ws/remote/:id`
> 桥接(`http.ts:346,368`)。**它没有开放公网入站端口** —— 抄这个判断。

### 2.2 身份:每个 runtime 一份可撤销凭据

**不是一个共享 token。** 每个注册 runtime 有独立身份,可单独撤销。

| 项 | 要求 |
| --- | --- |
| 注册 | 一次性注册码 → 换取长期凭据 |
| 凭据 | 每个 runtime 独立,**可单独撤销**而不影响其他 |
| 撤销 | 撤销后**立即**断连,不是等心跳超时 |
| 传输 | 远程访问必须有 TLS([00 §4](00-contracts.md#4-安全纪律)) |

> 今天的客户端 bearer(`cli-api-server.ts:158`)是**单进程共享**的。
> 多节点场景下共享凭据意味着**一个节点泄露 = 全部泄露**。
> **这是 Phase C 必须新建、不能沿用的部分。**

### 2.3 存在状态:区分"离线"和"崩了"

这是远程监控里唯一真正有价值的区分:

| 状态 | 判据 |
| --- | --- |
| `online` | 心跳在窗口内 |
| `graceful_offline` | 收到过显式停机信号 |
| `lost` | **心跳超时但从未收到停机信号** ← 这才是告警 |
| `draining` | 正在完成在跑的 run |

**把 `lost` 和 `graceful_offline` 分开,是这个功能的核心价值。**
只有一个 `online: false` 的远端监控等于没有监控 —— 用户分不清
"我关了它"和"它挂了"。

## 3. 远程监控到底指什么

### 3.1 观察

- 当前状态、正在跑的 run、历史
- 工具活动流(谁在什么时候调了什么)
- 资源占用(若 runtime 上报)

### 3.2 干预 ← **这才是核心价值,不要做成只读面板**

duya 已经有 `control-plane/approvals/`(600 目标树)。
**远端 runtime 跑一个危险工具时需要审批,而你人在手机前。**

```text
远端电脑:  run 需要审批 ──▶ 控制平面 ──▶ 推给已授权客户端
                                                    │
                              你在小程序上点"同意/拒绝" ◀┘
                                                    │
                          控制平面 ──▶ 回传 runtime ──▶ run 继续或中止
```

**这是"大号服务器运行或连接的基础"这句话最具体、也最难被别家替代的形态。**
只做只读监控的话,任何远程 MCP 客户端都能做;能做**审批介入**才锁住场景。

> **因此 C4(远程审批)优先级高于 C6(小程序)。**
> 小程序是更好的客户端形态,但先把"能审批"这件事在 web 端跑通,
> 再换客户端形态 —— 否则一次做两件新事,失败时无法归因。

### 3.3 不做

**远端桌面画面 / 摄像头 / 键鼠注入 —— 明确不做。**
`computer-use` 能力属于 runtime 内部(它已经在工具里),
**不因为 runtime 在远端就把屏幕流暴露给客户端。**
客户端只能看到 run 的状态与审批请求,看不到屏幕。

## 4. 传输

| 客户端 | 传输 | 依据 |
| --- | --- | --- |
| Electron renderer | IPC → HTTP 收敛(Phase B) | — |
| CLI | HTTP(已有) | — |
| `apps/web` | HTTP + **SSE** | 浏览器原生 `EventSource` |
| 小程序 | HTTP + **WebSocket** | §0.2,无 `EventSource` |
| runtime → 控制平面 | WebSocket 长连接 | §2.1 |

**单端口托管**(API + WS + 静态资源 + SPA 回退)照 ZCode
`packages/server/src/http.ts:399-414`,浏览器侧同源开一条 socket
(`packages/web/src/main.tsx:354-363` 是它的做法)。

### 4.1 小程序专属约束(实测,写进设计)

| 约束 | 影响 |
| --- | --- |
| **无 `EventSource`** | 必须 WS(§0.2) |
| **域名白名单** | `wss://` 域名必须先在后台配置;本地开发要勾"不校验" |
| **并发上限** | 同域名最多 5 条 WS,单个小程序最多 50 条 |
| **`setData` 代价高** | 跨线程通信,**必须节流**;不能每来一个 token 调一次 |
| **切后台断连** | `onClose`/`onError` 必须有重连,且重连后要续上下文 |

> **重连后续上下文**是最容易漏的一条:聊天/审批场景里,
> 断线重连后如果丢了待审批请求,用户会看到一个空面板,
> 以为"没有待办",而实际上有一个 run 卡在等审批。
> **这属于状态丢失,不是 UI bug。**

## 5. 门禁

| 门禁 | 检查 | 变异证明 |
| --- | --- | --- |
| **C1** runtime 身份独立可撤销 | 撤销 A 不影响 B;重复 id 被拒 | 复制一个 runtime id |
| **C2** 越权被拒 | 客户端 A 读不到 runtime B 的工作区 | 用 A 的凭据请求 B 的资源 |

### 5.1 C1 必须是行为门禁

不是"检查有没有 id 字段",而是:

- 注册两个 runtime,撤销其中一个 → **另一个仍然在线**
- 用同一个 id 注册两次 → **第二次被拒**

### 5.2 C2 必须跨身份实测

用 **A 的真实凭据**请求 **B 的资源**,断言被拒。
**不能只检查"有鉴权中间件存在"** —— 那证明不了隔离。

> 中间件存在 ≠ 隔离成立。同一个仓库里 G6 的已知盲区就是
> "扫 DDL 的 `NOT NULL`,证明不了生命周期已独立"
> (600 `README.md` §5.1「已知盲区」表的 **G6** 行;600 计划文档目前未跟踪,
> 行号会漂,故按小节引用)。**静态存在性证明不了运行期行为。**

   中止?继续?孤儿? **这条必须在实现前定,不能留到出问题再定。**
