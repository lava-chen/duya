# 00 — 合同

> 语义等价判据、不可协商的边界。**本文件是唯一权威。**

## 0. 为什么这份合同比迁移步骤重要

换驱动最危险的不是编译不过,是**静默的行为变化**:
语句照跑,结果不同;数字照出,精度变了;查询照发,顺序变了。

**SQLite 文件格式不变,只换绑定层** —— 这让"回滚"是可能的。
但**行为等价不自动成立**。本文件定义什么算"等价"。

## 1. 不可协商的三条

1. **不改 SQLite 文件格式。** 磁盘上的 db 文件在新旧驱动下都必须能打开。
   若任何一步需要 `VACUUM INTO` 重建文件才能打开,那是**缺陷**,不是迁移步骤。
2. **不改 schema、不改迁移逻辑。** 换驱动不是换 schema。
3. **不同时改查询。** 两个变量一起动,失败时无法归因。

## 2. 语义等价判据

### 2.1 值

| 类型 | 判据 |
| --- | --- |
| `INTEGER` | 超出 `Number.MAX_SAFE_INTEGER` 时**必须**能返回 BigInt 或显式报错,**不得静默截断** |
| `REAL` | 浮点结果必须逐位相同或差异可解释 |
| `TEXT` | 不得出现 `Buffer` 代替字符串 |
| `BLOB` | 不得出现 base64 字符串代替 Buffer |
| `NULL` | 必须仍是 `null`,不是 `undefined` 或空串 |

> **BigInt 是最可能静默出错的一处。** `node:sqlite` 在超出安全整数范围时
> 的行为必须**实测**并写进结果([01 Phase 0](01-migration-map.md#phase-0实测能力边界))。

### 2.2 集合

| 项 | 判据 |
| --- | --- |
| 行序 | **无 `ORDER BY` 的查询,顺序变化必须被显式接受或修正** |
| 列名 | 大小写与别名行为必须一致 |
| 空结果 | `all()` 返回 `[]` 而不是 `undefined` |
| `get()` 未命中 | 返回 `undefined` —— **与 better-sqlite3 逐字对齐** |

### 2.3 写入

| 项 | 判据 |
| --- | --- |
| `changes` | 必须等于实际受影响行数 |
| `lastInsertRowid` | 必须正确,尤其在事务内 |
| 事务 | 嵌套事务 / savepoint 语义必须一致 |
| `pragma` | 51 个文件的用法必须逐条验证,**尤其 `journal_mode` 与 `foreign_keys`** |

> **`pragma` 是 51 个文件的用量,仅次于 `close`。**
> `journal_mode=WAL`、`foreign_keys=ON`、`synchronous` 这几个错了不会报错,
> 只会让数据行为悄悄改变。**这类必须行为断言,不能只看"没抛异常"。**

### 2.4 生命周期 ← **本计划最大的风险**

`better-sqlite3` 的 `db.close()` 被调用 **73 次**。

`node:sqlite` 的 `DatabaseSync` **没有 `close()`** —— 它靠 GC 回收。

| 场景 | 要求 |
| --- | --- |
| worker 进程退出 | 无需显式 close(进程结束即回收) |
| 测试用例 teardown | **必须有确定性的清理方式**,否则测试间文件锁与状态泄漏 |
| 进程内重开同一文件 | **必须在旧句柄确定释放后才可重开**,否则 `SQLITE_BUSY` |

> **98 个 `db.close()` 不会编译失败 —— 它们会变成"什么都不做"。**
> 这是本次迁移**最可能静默失败**的点,也是 Phase 0 必须实测的项。
> 兼容层必须提供 `close()`,并在实现里明确说明它做了什么
> (例如同步 `PRAGMA wal_checkpoint(TRUNCATE)` 后依赖 GC),
> **不允许方法不存在**,也不允许它是个空函数假装成功。

### 2.5 自定义函数

`.function(` 有 2 处使用。`node:sqlite` 的用户函数注册方式与 better-sqlite3
不同,必须实测其**能否在 FTS5 触发器或索引表达式里被调用** ——
这是两种驱动行为差异最常见的地方。

## 3. 兼容层判据

Phase 1 写的 `db/driver.ts` 必须:

1. **对外暴露 better-sqlite3 的形状**,使 Phase 2 只改 import、不改逻辑
2. 实现 §2.2 里已用到的**全部** API(`.close` / `.prepare` / `.exec` /
   `.pragma` / `.transaction` / `.function` / `.serialize`)
3. 对每条判据**要么满足,要么显式抛错** —— **不许静默降级**
4. 自己带测试,覆盖 §2 全部条目

> **判据 1 是整个 Phase 2 便宜的原因。** 若兼容层暴露的是 `node:sqlite`
> 原生形状,177 个文件要逐个重写调用点,那是另一个量级的工作。
> **兼容层是"把重写一次"变成"改一行 import"的关键。**

## 4. 与 600 / 601 的边界

| 问题 | 归属 |
| --- | --- |
| SQLite 文件格式、schema、迁移 | **602** |
| 驱动绑定层与语义等价 | **602** |
| Session 身份解耦 | 600 |
| DB 路径不依赖 Electron | 601 Phase A |
| 控制平面 / 客户端契约 | 601 |

**602 不得改动 601 的任何结论。** 特别地:601 Phase A 里
`boot-config.ts` 与 `db/connection.ts` 的 Electron 解耦是**独立**改动,
602 只换驱动 —— 两者可以并行,互不阻塞。

> 反过来说:**若 602 顺手把 `db/connection.ts` 的 Electron 依赖也解耦了,
> 那是在抢 601 的 Phase A,并且让两者的失败无法归因。**
> 明确禁止。

## 5. 回滚要求

Phase 2 与 Phase 3 之间**必须**存在一个可操作的回滚路径:

| 项 | 要求 |
| --- | --- |
| 代码回滚 | 兼容层保留旧驱动路径,或 git revert 即可 |
| **数据回滚** | 换驱动**不得**让旧驱动打不开新驱动的文件 |

> **第 2 条是硬要求。** 若实测发现新驱动写过的文件 better-sqlite3 打不开,
> 那就是一个必须在 Phase 0 就暴露的阻断问题,而不是留到上线后才发现。
> **见 [01 Phase 0](01-migration-map.md#phase-0实测能力边界)。**
